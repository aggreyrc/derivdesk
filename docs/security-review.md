# DerivDesk — Phase 8 security review

**What this is:** a manual code review of `apps/api`, `apps/admin-api`, the web/admin SPAs, the database role design and the deployment files, against the areas in the project spec (authentication, authorization, credentials, multi-tenancy, financial operations, WebSockets, API abuse, OWASP). Findings were fixed where they could be fixed in code, with tests. **It is not a penetration test**, nothing was exercised against live infrastructure or a live Deriv account, and it does not replace an independent review before real money is involved.

Status key: **Fixed** (code + test) · **Mitigated** (reduced, residual noted) · **Open** (not fixed; reason given) · **OK** (checked, no change needed).

## Findings

| # | Area | Finding | Severity | Status |
|---|------|---------|----------|--------|
| 1 | Availability | `requireAuth` / `requireAdminAuth` were `async` middleware on Express 4, which does not catch rejected promises. A transient DB error during the session lookup became an unhandled rejection, which **terminates the Node process (≥ v15)** — taking the always-on bot runner and every WebSocket with it. Any user could trigger it by sending a cookie while the DB blipped. | High | **Fixed** (both apps; test simulates a dead DB and asserts a per-request 500) |
| 2 | Authentication | Admin 2FA was scaffolded but **not implemented** — an admin account was password-only. | High | **Fixed**: RFC 6238 TOTP, mandatory by default, single-use codes, atomic replay protection, enrol/recover via CLI (`npm run enroll-totp`). Production refuses to boot with 2FA off. Verified against the RFC 4226/6238 test vectors. |
| 3 | Financial | A withdrawal that **timed out, hit a 5xx, or returned an unparseable 2xx** had its local row *deleted* and was reported as failed — although Deriv may have accepted it. The user could then submit again. | High | **Fixed**: only a definitive Deriv 4xx rejection deletes the row; anything ambiguous keeps the `REQUESTED` row, audits `payments.withdrawal_outcome_unknown`, tells the user not to resubmit, and `GET /withdraw/:requestId` resolves it from Deriv. |
| 4 | Financial | In `withdraw()`, the audit write sat inside the same `try` as the Deriv call: if the audit insert failed **after Deriv accepted the withdrawal**, the `catch` deleted the row and reported failure. | High | **Fixed** (post-money steps moved out of the `try`). |
| 5 | Financial | A failed audit insert after a successful **buy/sell** returned a 500, telling the user the trade failed when it had happened. | Medium | **Fixed**: logged loudly with the full entry (`AUDIT_WRITE_FAILED`, for backfill) and swallowed. |
| 6 | Financial | No guard against an accidental double purchase (double-click, retry, two tabs). | Medium | **Fixed**: one buy in flight per user; a quote that already produced a purchase is refused (409) for 10 min. (App-level policy, not a claim about Deriv's behaviour.) Process-local — see Open. |
| 7 | Authorization | `derivdesk_admin` had no `DELETE` on `admin_sessions`, so admin **sign-out would fail** under the real least-privilege role (and my new session housekeeping / 2FA re-enrol need it). | Medium | **Fixed** in `001_roles.sql` (DELETE on `admin_sessions` only). |
| 8 | API abuse | Behind a load balancer every client shared the proxy's IP, so the per-IP rate limiters were one global bucket (or, with a naive `trust proxy: true`, spoofable via `X-Forwarded-For`). | Medium | **Fixed**: `TRUST_PROXY` = hop count (0–5), never a boolean. **You must set it** (usually `1`) in production. |
| 9 | API abuse | `buy` / `sell` / `proposal` had only the generic 120/min per-IP limit. | Medium | **Fixed**: per-**user** limiters (buy/sell 20/min, quotes 60/min). |
| 10 | Authentication | *(Superseded: password login removed.)* Login had no per-account throttle; per-IP 10/min alone does not stop a slow distributed guess at one account. | Medium | **Fixed**: failures counted per email+IP (5 / 15 min) and per email (20 / 15 min); blocked requests are refused *before* the password is checked. Applies to client and admin login. |
| 11 | Authentication | *(Superseded: password login removed.)* User-enumeration timing oracle: an unknown email skipped bcrypt, so it answered measurably faster than a wrong password. | Medium | **Fixed** (a dummy bcrypt comparison; both apps; test). |
| 12 | WebSockets | The gateway checked the session once, at upgrade. After logout, expiry or suspension the socket kept streaming balance and positions. | Medium | **Fixed**: logout closes that session's sockets immediately; every connection re-validates its session every 30 s (so a suspension takes effect within ≤ 30 s); close code `4401`. |
| 13 | WebSockets | `maxPayload` was the `ws` default (**100 MiB**); no limit on subscriptions, message rate or connections. Each tick subscription draws on the shared Deriv rate-limit budget. | Medium | **Fixed**: 1 KiB frames; ≤ 40 symbol and ≤ 20 contract subscriptions per socket; ≤ 20 msg/s (then closed 1008); ≤ 5 sockets per user; contract ids validated as safe positive integers; ping/pong heartbeat reaps dead peers; handshake socket errors handled. |
| 14 | OWASP A05 | Malformed JSON or an oversized body surfaced as **500** `InternalError` (and logged as a server error). | Low | **Fixed** (400 / 413). Body limits lowered (api 100 kB, admin 256 kB). |
| 15 | Observability | No request correlation id (spec §25). | Low | **Fixed**: `X-Request-Id` on every response, in every log line and in 500 bodies; inbound values accepted only if short and boring (no log/header injection). |
| 16 | Config | Production could boot with the placeholder `change_me_*` DB passwords, a non-https `CORS_ORIGIN`, or a placeholder `SESSION_SECRET`; admin with 2FA off. | Medium | **Fixed**: both apps refuse to boot in production on any of these (tests). `scripts/apply-roles.sh` can now set real role passwords. |
| 17 | Authentication | *(Superseded: password login removed.)* Emails were case-sensitive (`A@x.com` ≠ `a@x.com`) — duplicate accounts and a throttle bypass by varying case. bcrypt silently truncates passwords at 72 bytes. | Low | **Fixed**: emails trimmed + lower-cased at the boundary; passwords > 72 bytes refused at registration; login password capped at 1024. ⚠ Any pre-existing mixed-case email rows need lower-casing before this ships (none exist in a fresh deployment). |
| 18 | Sessions | Unbounded sessions per user; expired rows never purged. | Low | **Fixed**: oldest beyond 10 (client) / 3 (admin) revoked at login; expired rows pruned. |
| 19 | Exposure | `docker-compose.yml` published Postgres (`postgres/postgres`), Redis (no auth) and the admin ports on all interfaces. | Medium (dev) | **Fixed**: loopback-only. Dev compose only — still never publish a DB in production. |
| 20 | Web | Static SPAs had no security-header guidance (CSP, HSTS, frame-ancestors…); the Deriv redirect trusted the server-supplied URL's scheme. | Low | **Fixed**: `infra/nginx/security-headers.conf` (strict `script-src 'self'`); the SPA only navigates to `https:` authorization URLs. |

## Checked and fine (no change)

- **Multi-tenancy / IDOR.** Every Prisma read/write on user-owned data (`bot_instances`, `bot_trades`, `local_trades`, `payment_agent_withdrawals`, `deriv_accounts`, `watchlists`, sessions, tokens) is scoped by the session-derived `userId`; bot trades are only listed after an ownership check; the active Deriv account is always resolved from the verified session row — never from the request body, query or WebSocket message. No client-supplied user/account id or balance is trusted anywhere.
- **Credentials.** Deriv tokens are AES-256-GCM encrypted at rest (authenticated, random IV, versioned envelope); clients have **no passwords** (sign-in is Deriv OAuth only; the admin app keeps bcrypt + TOTP); no endpoint returns a token; pino redacts auth headers, cookies and token/password fields; the OAuth flow uses PKCE + state, single-use sealed cookie, constant-time state comparison, and never echoes Deriv's error text.
- **Admin boundary.** `derivdesk_admin` has no grant on `deriv_oauth_tokens`, `users`, `sessions`, `bot_instances`, `bot_trades`, `local_trades` etc., so a fully compromised admin app still cannot read client credentials or trade — enforced by Postgres, not app code. Admin and client use different DB roles, cookies, session tables and (now) different encryption keys. `derivdesk_api` cannot read `admin_users` and cannot update or delete `audit_logs`.
- **Cookies / CSRF.** Session cookies are `HttpOnly`, `Secure` in production, `SameSite=Strict`; CORS allows exactly one origin; bodies are JSON-only. There is no CSRF token — protection is SameSite + CORS (see Open).
- **Injection / XSS.** No raw SQL in app code (Prisma); strategy definitions are Zod-validated JSON with no `eval`; the SPAs contain no `dangerouslySetInnerHTML`, `innerHTML`, `eval`, or `localStorage`/`sessionStorage`.
- **Dependencies.** `npm audit --omit=dev`: 2 moderate, both `react-router` (open redirect via backslash in `<Link>`/`navigate`, and an SSR-hydration issue). Neither applies: the SPAs navigate only to fixed in-app paths and do no SSR. The fix is a major-version upgrade (v7) that I did not make blind; schedule it.

## Open / residual risks — read these

1. ***(Resolved in Phase 10, with a residual)*** Two API instances with `BOT_RUNNER_ENABLED=true` used to **trade every bot twice**. A Postgres lease (`runner_leases`, atomic acquire/renew on the database clock, self-fencing before expiry, re-checked immediately before every order; non-leaders never attach, even when asked via `POST /bots/:id/start`) now lets exactly one process lead, so the flag is safe on every replica. **Residual:** a process frozen between its last check and the network write of an order could send one order after losing the lease (microseconds wide; bounded by the stake ladder and stop-loss; no cross-system fencing token exists on Deriv's side). Verified against a real Postgres incl. 8-way races; see `docs/operations.md` §4.
2. The throttles, the **double-buy guard**, the analytics cache, the token-refresh de-duplication and the WS limits are **in-memory, per process**. With N instances each limit is effectively ×N, and a user's double-submit that lands on two instances **defeats the double-buy guard** unless routing is sticky per user. (The Phase 10 lease protects *bot* trading only.) Run one serving replica or add sticky routing; see `docs/operations.md` §4.3.
3. **Session ids are stored unhashed.** A read-only leak of the `sessions` table (SQL injection is not present, but a backup leak or a DBA) would allow hijacking live sessions. Hashing them is a contained change worth doing; not done here.
4. **No CSRF token.** Safe only while the web app and API are **same-site** (e.g. `app.example.com` + `api.example.com`). On unrelated domains the `SameSite=Strict` cookie would simply not be sent and sign-in would appear broken — deploy same-site.
5. ***(Superseded by the Deriv-only sign-up change)*** The registration-enumeration, password-reset and breached-password concerns no longer apply to clients: there is no registration or password. **New:** client identity rests on Deriv `account_id` uniqueness, which Deriv does not document (it documents no user id or email). `users.handle` is visible to the admin app (via `admin_visible_users`; email and hash are not). Mitigations: global unique index on `deriv_accounts.deriv_account_id`, owners >1 ⇒ `account_conflict` (never auto-merge), reconnect to another user's account ⇒ `account_mismatch`. Confirm the assumption with Deriv before launch.
6. ***(Moot)*** The per-email login lockout was removed with password login. The sign-in start endpoint is rate-limited per IP (10/min, per process). Login CSRF / session fixation are covered by the sealed, single-use, SameSite=Lax flow cookie + `state` + PKCE; the session cookie stays SameSite=Strict.
7. ***(Procedure added in Phase 10)*** `TOKEN_ENCRYPTION_KEY` / `ADMIN_TOTP_ENCRYPTION_KEY` rotate without downtime via decrypt-only `…_KEYS_EXTRA`, a compare-and-set re-encrypt command and a three-deploy sequence (`docs/operations.md` §7). **Still true:** backups taken before a rotation need the *old* key to be restorable, so it must be kept for the backup retention period.
8. A lost authenticator is recovered only by an operator with shell access re-running `enroll-totp` (that is intentional: no web path to bypass 2FA). There are no backup codes.
9. The audit log is append-only **for the application roles**; a Postgres superuser can still alter it. It is not tamper-evident.
10. `SESSION_SECRET` is required but currently unused (sessions are opaque random ids). It is kept so a future signed-cookie feature can't ship with a blank.
11. *(Superseded in Phase 10)* `scripts/apply-roles.sh`'s password step is replaced by `scripts/migrate-entrypoint.sh`, which refuses placeholder/short/identical role passwords, re-asserts grants and **fails the deploy (exit 70) if the admin/client privilege boundary is violated**. It is tested against a real Postgres (`packages/db/tests/migrateEntrypoint.test.ts`).
12. *(Found in Phase 9 and fixed)* `derivdesk_admin` lacked `INSERT` on `feature_flags` — creating a flag would have failed in production. Fixed in `001_roles.sql` and now guarded by `packages/db/tests/grantCoverage.test.ts`.
13. Not reviewed: the production images and compose file have **never been built or run** (no Docker daemon where they were written; `docker compose config` validates the compose file and the API image's runtime stage was simulated), the real Prisma query engine has never run against the app code, the Deriv-side behaviour of anything not verified against live docs, and third-party services. `docs/operations.md` §10 lists everything unverified.

## How the fixes are verified

`apps/api`: 240 tests (incl. 16 real-socket WebSocket gateway tests added in Phase 9) · `apps/admin-api`: 78 tests (65 new). New coverage includes HTTP-level tests through the real Express app (correlation ids, 400/413 mapping, a dead DB inside the auth middleware, 401 on protected routes, the login throttle short-circuiting before any DB lookup), TOTP against the published RFC vectors, replay and concurrent-use rejection, fail-closed enrolment, production-config refusals, the withdrawal ambiguity cases, and the WebSocket limiter/registry. All four apps typecheck and build.

## Phase 10 additions (deployment)

* **Admin isolation at the network layer, not only the database layer.** `admin-api` is attached only to Docker *internal* networks, so a compromised admin API has no route to the internet or to Deriv, and no published port. (This was initially wrong in the compose file — `admin-api` shared a non-internal network and would have had NAT egress — and was corrected and re-checked by parsing the resolved config.)
* **Production images:** multi-stage, non-root, read-only root filesystem with a tmpfs `/tmp`, `cap_drop: ALL`, `no-new-privileges`, memory limits, no compiler/tests/source in the runtime stage, no database owner credential in any long-running image (only the one-shot `migrate` job holds it). The `api` runtime stage excludes dev tooling; `admin-api` deliberately keeps `tsx` because the operator scripts run through it.
* **Migration safety:** `prisma migrate deploy` only; role passwords must be strong, distinct and non-placeholder or the deploy refuses; the boundary check runs on every deploy.
* **Observability without leaking data:** `/health` (liveness), `/ready` (database), and an unauthenticated **internal-only** metrics listener with no per-user or per-route labels.
* **Nothing here changes the open items 2–6, 8–10 above.**
