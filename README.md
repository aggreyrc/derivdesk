# DerivDesk

A Deriv trading and analysis platform where clients connect their own Deriv
account. This repo intentionally ships as **two fully separate deployments**:

| | Client app | Admin app |
|---|---|---|
| Frontend | `apps/web` (React/Vite, port 5173) | `apps/admin` (React/Vite, port 5174) |
| Backend | `apps/api` (Express, port 4000) | `apps/admin-api` (Express, port 4100) |
| DB role | `derivdesk_api` | `derivdesk_admin` (no grant on tokens/users/sessions/trades — see `infra/db-init/001_roles.sql`) |
| Identity | `users` / `sessions` | `admin_users` / `admin_sessions` (unrelated tables) |
| Account creation | **Sign in with Deriv** (`GET /api/deriv/login`) — there is no email/password sign-up | **No public endpoint** — `npm run create-admin --workspace apps/admin-api` only |

If you're looking for the architecture rationale (why this split, what's
verified against the live Deriv API, what's still open), see
[`docs/phase1-architecture.md`](./docs/phase1-architecture.md) — carried
over from Phase 1 unchanged.

## Prerequisites

- Node.js 22+
- Docker + Docker Compose (for Postgres/Redis locally), or your own Postgres 16

```bash
npm install
```

### Database

```bash
docker compose up -d postgres redis
```

The local Compose file does not run `infra/db-init/001_roles.sql` automatically:
it grants privileges on tables that must exist first. Apply the schema and then
create the application roles/grants:

```bash
npm run db:generate   # generates the Prisma client used by both backends
npm run db:migrate    # applies packages/db/prisma/migrations
npm run db:roles      # creates derivdesk_api / derivdesk_admin and applies grants
```

For a fresh local database, the role SQL uses the development passwords
`change_me_api` and `change_me_admin`. Ensure the `DATABASE_URL` in
`apps/api/.env` and `apps/admin-api/.env` uses the corresponding role password.
If those roles already exist, `db:roles` reapplies grants but does not reset
their passwords unless `DERIVDESK_API_DB_PASSWORD` and/or
`DERIVDESK_ADMIN_DB_PASSWORD` are set in the environment running that command.
The database password in `DATABASE_URL` is separate from the admin account
password passed to `create-admin`.

## Verification steps (what's actually been checked)

Run in this sandbox, network-permitting:

- `npm run typecheck` — clean for `apps/web` and `apps/admin` (no Prisma
  dependency). For `apps/api`/`apps/admin-api`, the **only** error you should
  see before running `db:generate` is `Cannot find module '@derivdesk/db'` —
  that's the ungenerated Prisma client, not a real bug; it resolves once you
  run `npm run db:generate`.
  **Caveat:** until the Prisma client is generated, anything typed through it
  (e.g. `apps/admin-api/src/modules/ops/ops.controller.ts`) resolves to `any`
  and is *not* really type-checked. Run `npm run db:generate && npm run typecheck`
  once as your first real verification of the backends.
- `npm test` — the auth-service unit tests (7 passing: 4 api, 3 admin-api) in both backends run against a
  mocked Prisma client and don't need a live database at all.
- `npm run build --workspace apps/web` / `--workspace apps/admin` — both
  should produce a working Vite production bundle.

## Why two deployments, concretely

It's not just `role: 'admin'` on a `users` row. Separation is enforced at
three layers, so a bug in one doesn't compromise the other:

1. **Identity** — `admin_users`/`admin_sessions` are separate tables from
   `users`/`sessions`, with no foreign key between them.
2. **Database privileges** — `derivdesk_admin` has no `SELECT` grant on
   `deriv_oauth_tokens`, `users`, `sessions`, `local_trades`,
   `transactions_cache`, `watchlists`, or `notifications` at all (see
   `infra/db-init/001_roles.sql`). It reads users through a column-limited
   `admin_visible_users` view (no `password_hash`) and can only change a
   user's `status` through a single SQL function, never a raw `UPDATE`.
3. **Network** — in `docker-compose.yml`, `admin`/`admin-api` sit on
   `internal_net`, `web`/`api` sit on `public_net`; only `postgres` bridges
   both. In production, put `admin`/`admin-api` behind a VPN or IP allowlist
   and never expose them the way `web`/`api` are exposed.

No code path in `apps/admin-api` calls Deriv's `buy`/`sell`/withdraw
endpoints at all — that capability is architecturally absent from this
deployment, not just permission-gated.

## Known limitations (Phase 2 scope)

- **Prisma CLI outputs are hand-authored**, not tool-generated — see the
  callout above. Regenerate once you have normal network access.
- **Admin 2FA (TOTP)** — was scaffolded here; implemented in Phase 8
  (see the Phase 8 section below).
- **No Deriv connection yet.** OAuth, OTP sessions, market data, trading,
  and payments are Phase 3 onward — this phase is auth + data model +
  deployment topology only. The routes/pages for those areas exist as
  placeholders so the IA from Phase 1 is already wired up.
- Docker images copy the whole monorepo and `npm install` inside the
  container rather than using per-package layer caching — fine for local
  dev, worth optimizing before a real CI/CD pipeline (Phase 10).
- `apps/admin-api`'s generated Prisma client technically exposes methods for
  tables it has no DB grant on (Prisma doesn't model per-role grants) —
  calling one of those from admin-api code will fail at the database, not
  silently succeed, but treat any such call as a bug to fix, not a pattern
  to build on.

## Sign-in with Deriv (replaces email/password sign-up)

There is **no registration form and no password login** for clients. A person signs up and signs in the same way: **Continue with Deriv** → `GET /api/deriv/login` → Deriv's OAuth2 (auth code + PKCE) → `GET /api/deriv/callback`. The first successful callback creates the user; later ones sign them in. `POST /api/auth/register` and `/api/auth/login` no longer exist (404).

**What identifies a user.** Deriv's documented token response contains only `access_token`, `expires_in` and `token_type` — no id_token, no email, no user id, no userinfo endpoint (checked against developers.deriv.com). So identity is the **set of Deriv account ids** the authorising token can see (`GET /trading/v1/options/accounts`):

| Situation at the callback | Result |
|---|---|
| No existing user owns any of the returned account ids | New user created (transaction); `handle` = first REAL account id, else first account id. Redirect `/?welcome=new`. |
| Exactly one user owns one or more of them | That user is signed in (new accounts on the token are added). `/?welcome=back`. |
| The ids belong to **more than one** user | `account_conflict` — we never merge users automatically. |
| Signed-in user reconnects Deriv and the token belongs to **another** user | `account_mismatch`. |
| User is suspended | `suspended` (audited). |
| Token lists no accounts | `no_accounts`. |

Failures redirect to `/login?deriv_error=<code>` (sign-in) or `/account?deriv_error=<code>` (reconnect) with a plain-language message. Rows are guarded by DB uniqueness (`users.handle`, and `deriv_accounts.deriv_account_id` globally) so two people can never share an identity even under a race.

**Flow security.** The flow state (`state`, PKCE verifier, who started it) lives in a sealed AES-GCM cookie (`derivdesk_oauth`: HttpOnly, SameSite=Lax, path `/api/deriv`, 10 minutes, single use), so the callback is bound to the browser that started it (login-CSRF / session-fixation protection). The session cookie (`derivdesk_session`, SameSite=Strict) is set by the callback response itself.

**Consequences — know these before launch**
* **Assumption to confirm with Deriv:** that a Deriv `account_id` is unique across all Deriv users and stays attached to the same person. It is not stated explicitly in the docs. If it were ever reassigned, the identity would be too.
* Users have **no email address** here, so there is no email verification, password reset or email notification feature (and nothing to leak). The admin UI shows the `handle` ("Deriv account") instead of an email.
* **Existing email/password users** (only relevant if you had any): the migration keeps their rows, but they can no longer sign in unless they connect a Deriv account that is already stored against them. Users whose Deriv account was attached to two users make the migration **stop** (see `docs/operations.md` §3).
* The legacy `users.email` / `users.password_hash` columns are kept as nullable, unused columns (expand step) and should be dropped in a later "contract" migration. `audit_logs.actor_email` still exists and now holds the handle.
* Not tested against live Deriv; the sign-in logic is tested against an in-memory database with the same unique constraints plus the real-Postgres constraint/migration tests in `packages/db`.

## Phase 3 — Deriv OAuth connection (client app only)

`apps/api` now implements the Deriv side of "connect your own account":

- **`GET /api/deriv/connect`** — builds a PKCE `authorize` URL and seals the
  verifier + CSRF `state` into a short-lived, `SameSite=Lax`, encrypted
  cookie (`derivdesk_oauth`, scoped to `/api/deriv`, 10-minute TTL). Sealed
  rather than session-bound because the callback is a cross-site top-level
  navigation, so the app's own `SameSite=Strict` session cookie isn't sent on
  it — see the comment in `deriv.service.ts`/`oauthState.ts` for the full
  reasoning.
- **`GET /api/deriv/callback`** — verifies `state` (timing-safe compare),
  exchanges the code, encrypts the resulting tokens at rest
  (AES-256-GCM, versioned envelope, `crypto.ts`), and redirects the browser
  back into the SPA with only a safe, enumerated error code in the URL —
  never Deriv's free-text `error_description`.
- **`GET /api/deriv/accounts`** — the reconciled account list. **A newly
  connected or newly logged-in session is only ever auto-activated onto a
  DEMO account.** If a user has only real accounts, nothing is auto-selected
  — there is no code path that defaults a session onto real money.
- **`POST /api/deriv/accounts/:id/activate`** — switching to a REAL account
  requires an explicit `confirmReal: true` in the request body; the client
  UI backs this with a native confirm dialog. Every account id is scoped to
  `req.userId` from the verified session before use (tested against IDOR).
- **`POST /api/deriv/accounts/refresh`** — re-pulls from Deriv (source of
  truth); accounts Deriv stops returning are marked `unavailable`, never
  deleted (they may carry trade history).
- **`DELETE /api/deriv/connection`** — forgets the connection on our side.
- Access-token refresh is single-flighted per user (`getValidAccessToken`)
  and distinguishes a **definitive** rejection (4xx → mark `needsReauth`,
  audit it, ask the user to reconnect) from a **transient** one (5xx/timeout
  → surface `DerivUnavailable`, leave the connection alone). One Deriv
  connection per app user is enforced with a DB-level unique constraint, not
  just application logic.
- `apps/web`'s `/account` page drives the whole flow, and a demo/real badge
  next to the app name in the sidebar (`AppShell.tsx`, polled every 30s via
  `derivStatus.tsx`) is visible on every page, not just `/account` — so
  which environment is active is never something you have to go look up.

**Verified against the live Deriv docs while building this** (see
`docs/phase1-architecture.md` §0/§2 for the full writeup of why the legacy
"authorize on a socket" model doesn't apply here): the authorization-code +
PKCE exchange, the account-list REST call, and the response shapes parsed in
`deriv.client.ts`. **Not verified against a live Deriv app** (no test
credentials were available while building this): the refresh-token grant —
Deriv's docs mention a `refresh_token` is issued but don't document the
refresh request itself, so `DerivClient.refresh()` follows plain RFC 6749 §6
and is flagged in its own doc comment. Test this against a real Deriv app
before relying on it, and adjust `refresh()` if Deriv's actual behavior
differs.

**apps/admin-api is untouched by Phase 3 by design** — no Deriv credential,
token, or connection code exists in that deployment at all, matching the
Phase 1 admin-dashboard decision.

### New Phase 3 tests (32 total now, up from 7)
IDOR on account activation, the real-account confirmation gate, CSRF
`state` mismatch, expired/tampered OAuth cookies (AES-GCM tamper detection
and TTL expiry), the demo-only auto-activation rule, 4xx-vs-5xx refresh
classification, and reconciliation (Deriv-absent accounts marked
unavailable, not deleted).

### New Phase 3 known limitations
- **Refresh-token grant is unverified** (see above) — the single biggest
  thing to test against a real Deriv app before production.
- The demo/real badge polls every 30s rather than pushing updates — Phase 4
  replaces this with the WebSocket gateway's `CONNECTION_CHANGED`/
  `BALANCE_UPDATED` events.
- The real-account confirmation is a native `confirm()` dialog — functional,
  but the polished confirmation UI belongs in Phase 5+ (trading) once the
  rest of the trade-confirmation pattern exists.
- Single-flight refresh dedup is in-process only; scaling `apps/api` beyond
  one instance needs a DB advisory lock or Redis lock around it (flagged in
  `deriv.service.ts`).
- OTP/WebSocket session handling itself (`DerivClient.requestOtp` is written
  but unused) is Phase 4 — this phase only gets a valid *access token* and
  the account list.

## Phase 4 — Market data (public gateway only; no Deriv auth involved)

Two corrections came out of building this phase, both worth reading before
Phase 5:

1. **The rate-limit figures in `docs/phase1-architecture.md` §2 were wrong**
   and have been corrected in place there (with a note explaining the fix).
   It's not "5 connections/user, 100 subs/connection" — Deriv's actual
   [Limits page](https://developers.deriv.com/docs/limits/) documents
   **shared per-minute/per-hour budgets by call group** (e.g. `active_symbols`
   + `ticks` + `ticks_history` together draw on one 220/min budget *for the
   whole app*, not per user). `MarketDataGateway` is built against the
   corrected numbers: `slidingWindowLimiter.ts` paces every one-shot request
   through that shared budget with a safety margin, and — because there's no
   documented connection-count cap — the pooled single connection exists to
   protect that shared *rate* budget, not to stay under a connection limit.

2. **Deriv's own current docs contradict themselves on WS authentication**,
   found while cross-checking market data against `/docs/` rather than only
   the `/llms/` concept guides used in Phase 1. The dedicated
   [`WebSocket demo`](https://developers.deriv.com/docs/options/ws-demo/)/
   `ws-real` pages describe the OTP-URL model Phase 3 was built against (no
   `authorize` message — the URL itself is the credential). But the
   [Best practices](https://developers.deriv.com/docs/best-practices/) page,
   part of the same current doc set, shows `socket.send({authorize: "<token>"})`
   as the way to authenticate. **This is flagged, not resolved** — it doesn't
   block Phase 4 (the public gateway this phase uses is unauthenticated,
   confirmed unambiguously at
   [`/docs/options/ws-public/`](https://developers.deriv.com/docs/options/ws-public/):
   "Account-scoped actions such as placing trades or reading balances aren't
   available on this channel"), but it's a real open question for Phase 5's
   authenticated `ws/real`/`ws/demo` connections. Test both against a live
   Deriv app before Phase 5 ships: try the OTP URL alone first; if
   account-scoped calls (`balance`, `portfolio`) come back
   unauthorized, send `authorize` with the decrypted OAuth access token as a
   fallback and see which one Deriv actually honors.

### What's built
- **`derivPublicClient.ts`** — the wire-protocol client for Deriv's
  unauthenticated `wss://api.derivws.com/trading/v1/options/ws/public`
  gateway: `req_id` correlation (checked at both `response.req_id` and
  `response.echo_req.req_id` — different endpoints were observed doing
  either), 30-second ping keepalive, and exponential-backoff reconnect that
  calls back into `MarketDataGateway` so subscriptions are restored
  automatically.
- **`market.gateway.ts`** — the one shared instance
  (`market.instance.ts`) every app user's market data flows through.
  `getActiveSymbols()` (30s cache), `getCandles()` (one-shot, `subscribe: 0`),
  and `subscribeTicks()` (ref-counted — ten browser tabs watching `R_100`
  costs Deriv exactly one subscription, and `forget` is only sent once the
  last one unsubscribes).
- **Response shapes verified, not assumed** — Deriv's current API renamed
  fields from the legacy shape (`symbol`→`underlying_symbol`,
  `symbol_type`→`underlying_symbol_type`) and changed which tick fields are
  required; `market.schemas.ts`'s Zod schemas were checked line-by-line
  against
  [`/comparison/active-symbols/`](https://developers.deriv.com/comparison/active-symbols/)
  and [`/comparison/ticks/`](https://developers.deriv.com/comparison/ticks/),
  which show old-vs-new field diffs directly — a more reliable source than
  guessing from either shape alone.
- **`apps/api/src/ws/wsGateway.ts`** — Hop 1 (`docs/phase1-architecture.md`
  §8): the browser-facing WebSocket gateway. Authenticates at the HTTP
  upgrade using the same session cookie as the REST API (no separate
  login), checks `Origin` manually (a WS upgrade has no CORS preflight to do
  it for you), and speaks only the two normalized events this phase needs —
  `MARKET_TICK`, `CONNECTION_CHANGED` — never a raw Deriv message shape.
- **`apps/web`**: `/markets` — symbol search, a watchlist (backed by the
  `watchlists`/`watchlist_items` tables from the Phase 1 schema, previously
  unused), live prices over the WS gateway, and a candlestick chart
  (`lightweight-charts`) fed by `ticks_history`.

### New Phase 4 tests (22 more — 54 total)
`derivPublicClient`: req_id correlation both ways, error-frame rejection,
request timeout, backoff reconnect + resubscribe callback, immediate
rejection of in-flight requests on disconnect, no-reconnect-after-explicit-close,
ping cadence. `market.gateway`: current (non-legacy) field parsing, rejects
malformed responses instead of passing them through, one-shot vs. streaming
requests, ref-counted subscribe/unsubscribe (including the "still one
listener left → no `forget`" case), stale-tick suppression after

immediate execution under budget, FIFO queueing past it.

### New Phase 4 known limitations
- **The authorize-vs-OTP contradiction above** is the one to resolve first
  in Phase 5.
- The candlestick chart loads a snapshot on selection/timeframe change; it
  doesn't yet redraw the currently-forming candle from live ticks (the
  price ticker above it does update live). Full live-candle aggregation is
  reasonable to fold into Phase 7 (Analysis) rather than duplicate here.
- `contracts_for`/`contracts_list` (the endpoints that describe which
  contract types and parameters a symbol actually supports) are deferred to
  Phase 5, where they're needed to build the trade ticket.
- The outbound rate limiter is in-process only, same caveat as Phase 3's
  refresh dedup — scaling `apps/api` beyond one instance needs a shared
  (Redis-backed) limiter instead.
- `apps/admin-api`/`apps/admin` are untouched by this phase — market data is
  client-only, as designed.

## Phase 5 — Trading (authenticated)

This phase builds the actual trading path: a price quote, a buy, a sell, a
live portfolio, and trade history — all against the user's own, explicitly
activated Deriv account, never a pooled or app-owned one.

**The authorize/OTP contradiction flagged in Phase 4 is still unresolved —
deliberately.** No test credentials were available while building this, so
rather than guess which of Deriv's two self-contradicting current docs is
right, `DerivPrivateClient` (`apps/api/src/modules/trading/derivPrivateClient.ts`)
does both: it connects on the account's freshly-requested OTP URL (the
primary, documented mechanism) and then sends a defensive `authorize` with
the decrypted OAuth access token afterward, recording whichever outcome
actually happens as `lastAuthorizeOutcome` (`"accepted" | "rejected"`). If
`authorize` is rejected or errors, the connection is **not** closed — it
proceeds on the OTP URL's own authentication, which Deriv's ws-real/ws-demo
pages describe as sufficient by itself. **Before this goes anywhere near
production**: connect a real Deriv app, watch which outcome gets logged
("defensive `authorize` on OTP-issued Deriv connection"), and once it's
consistent, delete whichever half of this isn't needed.

### What's built

- **`derivWsClient.ts`** — Phase 4's `derivPublicClient.ts` wire-protocol
  logic (req_id correlation, 30s ping, backoff reconnect) generalized into a
  shared base class, parameterized on a URL *provider* function instead of a
  fixed URL string. `DerivPublicClient` now just closes over a constant;
  `DerivPrivateClient` (below) calls Deriv's OTP endpoint fresh on every
  connect — including every reconnect, since OTP URLs are one-time and
  can't be cached. This refactor was verified against Phase 4's full
  existing test suite before anything new was built on it (two real
  timing/wiring bugs were caught doing that — see git history on this file
  if you need the specifics — and all 19 Phase 4 tests still pass
  unchanged).
- **`trading.sessionManager.ts`** — owns every authenticated per-
  `(user, derivAccount)` Deriv connection. Mirrors `MarketDataGateway`'s
  ref-counted subscription sharing (ten browser tabs watching the same
  contract costs one upstream `proposal_open_contract` subscription,
  `forget` only on the last unsubscribe) and adds a **10-second idle
  teardown**: unlike the one shared public connection, there's no reason to
  keep a user's authenticated session (and its OTP-refresh/ping traffic)
  alive once nothing is watching it. `buy`/`sell`/`getPortfolio`/
  `getProfitTable` each acquire the session, send one request, and release
  it; a single short retry (`requestWithRetry`) absorbs the race where a
  request lands just as a reconnect's fresh OTP URL is still being fetched.
- **`market.gateway.ts` gained `getContractsFor()` and `getProposal()`** —
  both confirmed **no-auth** Deriv calls (`auth_required: 0` in
  [`proposal_request.schema.json`](https://developers.deriv.com/schemas/proposal_request.schema.json);
  the "No Auth" badge at
  [`/comparison/contracts-for/`](https://developers.deriv.com/comparison/contracts-for/)),
  so they ride the same pooled public connection and shared rate-limit
  budget as ticks/candles rather than opening a private connection just to
  ask "what can I trade" or "what would this cost". `getProposal()`'s
  response schema only requires `id` — everything else (`ask_price`,
  `payout`, `longcode`) is advisory display data; the price actually paid is
  whatever `buy` itself confirms.
- **`POST /api/trading/proposal|buy|sell`, `GET /api/trading/portfolio|history`**
  (`trading.controller.ts`/`trading.routes.ts`) — every one of these resolves
  the account to trade on from `req.sessionId`'s `activeDerivAccount` row,
  **never** from anything the client supplies in the request body; buying on
  a REAL account requires `confirmReal: true` in the body (same pattern as
  Phase 3's account activation), and the client UI backs it with a
  confirmation dialog quoting the actual price. A successful buy/sell writes
  a best-effort row to `local_trades` purely as a cross-session "what do I
  hold" convenience cache — it is never read back as the source of truth;
  `portfolio`/`history` always re-ask Deriv directly.
- **WS gateway (`apps/api/src/ws/wsGateway.ts`)** gained `BALANCE_UPDATED`,
  `POSITION_UPDATED`, and `TRADE_ERROR`. Balance streams automatically for
  the session's active account as soon as the socket authenticates (no
  client request needed); per-contract P/L streams on request
  (`SUBSCRIBE_POSITION`/`UNSUBSCRIBE_POSITION`), with the same
  never-trust-the-client-account-id rule as the REST layer — the account id
  is re-resolved from the verified session every time, not taken from the
  message. `CONTRACT_UPDATED` (contract-settlement notifications distinct
  from live P/L) and full `TRANSACTION_UPDATED` streaming are deferred —
  see known limitations.
- **`apps/web`**: the Markets page's trade ticket (contract type driven
  entirely from `getContractsFor` — the form can never offer a combination
  Deriv doesn't support for that symbol), a two-step quote-then-buy flow
  that re-sends the exact quoted price, and a native confirm dialog before
  any real-money buy. `/portfolio` shows open positions with live P/L over
  the WS gateway and a sell button; `/transactions` shows closed trades from
  Deriv's own `profit_table` (never computed from the local cache). The
  sidebar's balance figure switches from the Phase 3 cached/polled value to
  the live `BALANCE_UPDATED` push the moment one arrives.

subscriptions (including the "still one listener → no `forget`" case and
delivering a push only to that contract's own listeners), balance fan-out
to every listener on a session with no cross-user leakage. `market.gateway`:
current (non-legacy) `contracts_for`/`proposal` shapes, rejects malformed
responses, `proposal`'s "only `id` is guaranteed" rule.

### Known limitations

- **The authorize/OTP contradiction is still open** — see above. This is
  the single biggest pre-production verification item carried out of this
  phase.
- **`CONTRACT_UPDATED`/full `TRANSACTION_UPDATED` streaming are deferred.**
  Phase 5 streams live position P/L (`POSITION_UPDATED`) and balance, which
  covers the portfolio page; a dedicated settlement-notification event and
  full transaction-stream relaying (beyond the `profit_table` the history
  page already pulls on load) are reasonable to add alongside Phase 7's
  analytics work rather than duplicate here.
- **`requestWithRetry`'s one-shot retry is a narrow fix for one race**
  (a request landing just as a fresh reconnect's OTP URL is still being
  fetched) — it is not general resilience against a down Deriv connection,
  and a caller can still see a rejected promise if the account is
  genuinely unreachable.
- **In-process only, same caveat as Phases 3/4**: `TradingSessionManager`'s
  session map lives in one `apps/api` process. Scaling beyond one instance
  needs either sticky routing per user or moving session state to something
  shared (Redis) — not attempted here.
- **The trade ticket's barrier input is a free-text field**, not validated
  against `contracts_for`'s declared barrier ranges before submission —
  Deriv's own `proposal` rejection is the actual validation; the UI doesn't
  duplicate it.
- **`apps/admin-api`/`apps/admin` are untouched by this phase** — trading is
  client-only, matching every prior phase's admin-dashboard boundary: admin
  never gets a code path that could place a trade on a client's behalf.

## Phase 6 — Payments (payment-agent withdrawals only)

### What's built

- **`apps/api`'s `DerivClient` extended with the payment-agents REST surface**
  (`/payment-agents/v1/...`) — a separate surface from the `/trading/v1/options/*`
  API used by Phases 3-5, but verified field-by-field against live
  `developers.deriv.com` schema/docs pages the same way: `listPaymentAgents`,
  `requestWithdrawalOtp` (triggers Deriv to send a 6-digit code **directly to
  the user** — never through this app), `withdrawViaPaymentAgent`,
  `getWithdrawalStatus`. Every response is Zod-parsed; an unexpected shape is
  a `502 UnexpectedResponse`, never silently coerced.
- **`/api/payments` module** (`apps/api`): `GET /deposit-link`,
  `GET /agents`, `POST /withdraw/verification-code`, `POST /withdraw`,
  `GET /withdraw/:requestId`, `GET /history` — all behind `requireAuth`, and
  the two POST endpoints behind the same `authLimiter` used for other
  sensitive actions.
- **Real-account-only gate**: every payments operation resolves the active
  Deriv account from the session (never from anything the client supplies)
  and rejects a DEMO account outright — Deriv's payment-agent network doesn't
  operate on demo balances. Currency is always the account's own currency,
  never client-supplied.
- **No fiat deposit API and no direct bank/card withdrawal API exist**
  (re-confirmed directly against live Deriv docs, consistent with Phase 1's
  architecture doc) — deposits deep-link to Deriv's own cashier
  (`GET /deposit-link`); payment-agent withdrawal is the only withdrawal path
  this app can reach over an API.
- **Write-before-call, delete-on-failure for withdrawals**: a `REQUESTED` row
  is written to our DB *before* calling Deriv, so a withdrawal Deriv actually
  accepted but whose confirmation we failed to receive (timeout, crash) stays
  visible as "requested" rather than silently lost. If the Deriv call fails
  outright, the row is deleted again and Deriv's own rejection reason (bad
  code, over a limit, rate-limited) is surfaced, not reworded into something
  vaguer.
- **`request_id` idempotency**: generated server-side via `randomUUID()` per
  attempt, never reused on retry — reusing one is a `RequestIDUsed` error on
  Deriv's side.
- **Every financial action is audited**: OTP requests, successful
  submissions, and failures all write an `audit_logs` row (`payments.*`
  actions).
- **`apps/web`'s `/payments` page**: a deposit deep-link button; an
  agent-selection + amount form that only renders when the active account is
  REAL (otherwise a plain explanation and a link to switch accounts); the
  OTP-then-verify-then-confirm flow, with a `window.confirm` gate before the
  final submit (same real-money-confirmation pattern as Phase 5's buy flow);
  and a withdrawal history table with a per-row "Refresh" that re-polls
  Deriv's own status for anything still `REQUESTED`/`PENDING`.
- **`apps/admin-api`/`apps/admin`'s read-only withdrawals view**
  (`GET /api/admin/withdrawals`, filterable by status) was already scaffolded
  in Phase 2 against the Phase 1 schema and needed no backend changes — this
  phase built the admin frontend page that actually renders it. It is
  strictly read-only: no endpoint exists anywhere in `apps/admin-api` that can
  initiate, approve, or cancel a withdrawal, matching the hard rule that
  admin never acts on a client's behalf. `derivdesk_admin`'s Postgres role has
  `SELECT` only on `payment_agent_withdrawals` and no grant at all on
  `deriv_oauth_tokens` (see `infra/db-init/001_roles.sql`).

### Tests

9 new tests in `apps/api/src/modules/payments/payments.service.test.ts`,
covering: the real-account-only gate on listing agents and on both withdrawal
calls; OTP request happy path + audit; the write-REQUESTED-then-update
pattern on a successful withdrawal; row deletion + 422 surfaced on a Deriv
rejection; the IDOR-safe 404 on someone else's `request_id`; skip-repoll once
a withdrawal has settled; and refresh-from-Deriv on an unsettled one. Full
`apps/api` suite at the end of the payments work: **82/82 passing** (73 carried over + 9 new), zero
regressions. `apps/api`, `apps/web`, and `apps/admin` all typecheck and build
clean.

### Known limitations

- **The deposit-link URL (`https://app.deriv.com/cashier/deposit`) is not
  verified against a live, logged-in Deriv session** — a headless fetch to it
  (unauthenticated) just redirects to the marketing site, which is
  inconclusive for an SPA route. Every other payments endpoint here is
  schema-verified field-by-field; this one URL is the best-available address
  and is flagged in code (`payments.controller.ts`) as needing a check
  against a real logged-in account before production use.
- **No Deriv-side push for withdrawal status changes** — the history page's
  "Refresh" button does a pull (`GET /withdraw/:requestId`) rather than
  anything pushed over the WebSocket gateway. A `WITHDRAWAL_UPDATED` WS event
  would remove the need to click it, but wasn't in this phase's scope.
- **`apps/admin-api`/`apps/admin` gained no new backend code this phase** —
  the read-only withdrawals endpoint and its DB grant already existed from
  Phase 2's scaffolding; only the admin frontend page was built against it.

## Bot trading (built alongside Phase 6)

Requested together with Phase 6: add the uploaded Deriv DBot strategy to the
site, and let an admin add bots. Three decisions were confirmed up front:
**server-side always-on execution**, **admin manages a strategy catalog only**,
and **a general strategy framework** (the DBot strategy is the first entry, not
the only one).

### The boundary that matters

- **Admin owns templates (`BotStrategy`) and nothing else.** `apps/admin-api`
  exposes CRUD for the catalog (`/api/admin/bot-strategies`) and has **no
  database grant** on `bot_instances` or `bot_trades`
  (`infra/db-init/001_roles.sql`). It cannot see, start, stop, or trade any
  user's bot, and cannot see any Deriv credential. New strategies are created
  as `DRAFT`; publishing is a separate, confirmed step. `DELETE` on
  `bot_strategies` is granted only to undo a mistaken draft: an in-use strategy
  is protected by `ON DELETE RESTRICT`, and archiving is how you retire one.
- **Users own instances (`BotInstance`).** Each user picks a *published*
  template, chooses one of their *own* accounts, and sets their own stake and
  kill switches. The account and strategy are fixed at creation (a "demo" bot
  can never be re-pointed at real money). Every query is scoped by `userId`;
  another user's bot is a 404.

### What's built

- **Strategy framework** (`apps/api/src/modules/bots`): a JSON
  `StrategyDefinition` (indicators SMA/EMA/RSI/MACD, entry rules as a small
  all/any condition tree with GT/LT/crossover operators, staking, risk limits,
  trade duration), validated by Zod. **Not an expression language** — no eval;
  a malformed definition can only fail validation. New *combinations* of the
  supported indicators are a data change (new catalog row); a genuinely new
  indicator type still needs code in `indicators.ts` + `signalEngine.ts`.
  `apps/admin-api` holds a byte-for-byte copy of the schema on purpose (the two
  deployments share no runtime code) — change both together.
- **Always-on runner** (`botRunner.ts`): evaluates each `RUNNING` instance on
  **closed candles only, once per candle**, one open trade per instance, using
  the existing `MarketDataGateway` (candles, proposals) and
  `TradingSessionManager` (buy, settlement stream). State (ladder step, session
  P/L, open trade) is in the database, so a restart resumes exactly where it
  was (`start()` re-attaches `RUNNING` bots and resumes watching any `OPEN`
  trade). **Fails closed**: bad config, lost Deriv auth, a trade that never
  settles, a trade that couldn't be recorded, or five errors in a row all
  *stop* the bot with a stated reason instead of guessing. A quote above the
  configured stake is refused. A real account is re-checked on every trade.
  Pausing/stopping mid-trade keeps watching the open trade until it settles,
  then records the outcome without overwriting the user's status.
- **Kill switches**: stop-loss, target profit, max consecutive losses, max
  trades, and stake-ladder exhaustion. A bot with neither a stop-loss nor a
  target profit is refused, and a setup whose peak stake exceeds 1000 is
  refused.
- **User API** (`/api/bots`): catalog, list/create/update/delete, start/pause/
  stop, trades. Real-money accounts need explicit confirmation **at creation
  and again at every start**; at most 3 bots run per user; `start` is
  rate-limited and audited (`bots.*` actions).
- **UI**: `apps/web` `/bots` (create form with a live "largest stake this setup
  can reach" figure and a plain martingale warning, status cards, trade list;
  demo account preselected, REAL needs a ticked acknowledgement + a confirm
  dialog on start) and `apps/admin` `/bots` (catalog list, create/edit with a
  JSON definition editor prefilled from a known-valid example, publish/
  archive/delete with confirmations).
- **Operational kill switch**: `BOT_RUNNER_ENABLED=false` stops the runner from
  starting; running bots stay `RUNNING` in the database and resume when it is
  re-enabled.

### Tests

66 bot tests in `apps/api` (indicators, signal engine, staking/risk,
runner, user service) and 10 in `apps/admin-api`. Whole repo: **api 148/148,
admin-api 13/13**; all four apps typecheck and build clean.

### Known limitations — read before turning this on

- **The original DBot XML was not available in the working session**, so the
  built-in definition (`strategies/emaRsiMacdMartingale.ts`) uses conventional,
  clearly labelled parameters (EMA 10/25, RSI 14, MACD 12/26/9, 2x martingale)
  for the *same strategy shape*, not the file's exact thresholds. Re-upload the
  XML to match it exactly. It is **not seeded**: create it from the admin
  "New strategy" screen (the starter JSON is prefilled), review it, publish it.
- **Never run against live Deriv.** Everything is unit-tested with mocked
  Deriv; the real buy → settlement stream lifecycle has not been exercised.
  Run a bot on a **demo** account for a while before trusting it with real
  money.
- **Multiple `apps/api` instances are now safe for bots** (Phase 10): a Postgres
  lease lets exactly one lead, so two instances cannot double-trade. Other
  per-process state is still not shared — see docs/operations.md §4.3 before
  running more than one replica that serves users.
- **Martingale can lose quickly.** The UI shows the peak stake and caps it, but
  a losing streak of `maxSteps` trades is a real outcome, not an edge case.
- **Prisma client**: the sandbox could not run `prisma generate`, so
  `packages/db/generated/client/bot-models.d.ts` is a hand-written typing shim
  and the `20261013000000_bot_trading` migration is hand-authored and has not
  been applied to a live Postgres. After `npm run db:generate` and
  `db:migrate:deploy` somewhere with network access, **delete the shim** and
  its `/// <reference>` line.
- **Contract types** are limited to CALL/PUT (rise/fall); digits, touch, and
  multiplier strategies are future extensions.
- **Polling, not push**: the bots page refreshes every 5 seconds rather than
  over the WebSocket gateway. No edit screen on the client yet (the API
  supports `PATCH`; delete and recreate for now).

## Phase 7 — Analytics (performance + technical analysis)

Everything here is read-only: no endpoint in this phase places, changes or cancels anything.

### What's built

**Performance analytics** — `GET /api/analytics/summary` and `/performance` (`?period=7d|30d|90d|all`, default 30d)
- Built from Deriv's own `profit_table` (request/response fields verified against the live API schema). Per-trade P/L is plain `sell_price − buy_price`; nothing is estimated.
- Summary: trades, wins/losses/breakeven, win rate, net P/L, gross profit/loss, profit factor, average win/loss, expectancy, largest win/loss, total staked, longest win/loss streaks, max drawdown.
- Performance: cumulative P/L series plus breakdowns by UTC day, symbol, contract type, and **Bot vs Manual** (a trade is "Bot" when its `contract_id` matches one of the user's own `BotTrade` rows).
- Scope is the user's **active account only**; every response carries `meta.accountType` (DEMO/REAL), account id and currency, and the UI shows a demo/real badge. Demo and real are never blended.
- Rows Deriv returns without a usable price or settle time are **excluded and counted** (`meta.excludedRows`), never guessed. The UI says so.
- Safeguards: 2000-trade cap (4 pages × 500; `meta.truncated` flags it), `date_to` pinned to "now" so paging is stable, 60 s in-memory cache keyed by user + account + period. Account is resolved from the session server-side — no user/account id is accepted from the client (409 if none is active).

**Technical analysis** — `GET /api/analytics/technical?symbol&granularity&count`
- SMA 20, EMA 20/50, RSI 14, MACD 12/26/9 over Deriv candles, using the same indicator functions the bots use. Fixed conventional parameters (not user-tunable).
- Readings are descriptive only (price vs EMA, RSI zone, MACD histogram sign). No buy/sell language, no forecasts; the UI states this.

**Web** — the Analysis page has a Performance tab (period selector, tiles, cumulative P/L chart, breakdown tables, truncation/exclusion notices) and a Technical tab (symbol + 1m/5m/1h/1d, candles with SMA/EMA overlays, RSI and MACD panes with synced time ranges).

### Tests
- api: 177 passing (+27 this phase: analytics engine 12, service 8, technical 7, plus 2 profit-table session-manager tests). admin-api: 13 passing. All four apps typecheck and build.

### Known limitations
- Computed on demand from Deriv, not stored: the `analytics_snapshots` table is not used yet, so history is limited to what the profit table returns (and the 2000-trade cap).
- Only **settled** contracts appear (that is what `profit_table` contains). Open positions are on the Portfolio page.
- Days are UTC. Display decimals: 2 for fiat/USD stablecoins, otherwise 8.
- Cache is per-process; with multiple API instances each keeps its own 60 s cache.
- Bot-vs-Manual relies on `BotTrade.contract_id`; a bot trade that failed to record (the bot stops with TRADE_RECORD_FAILED) would show as Manual.
- Never exercised against a live Deriv account from this sandbox — the request/response handling is unit-tested against the documented schema only. Run a demo account through it before relying on the numbers.
- Technical analysis shows what indicators currently read; it is not a signal or advice.

## Phase 8 — Security hardening

A full write-up — 20 findings with severity and status, what was checked and found fine, and the **open risks** — is in [`docs/security-review.md`](docs/security-review.md). Read its "Open / residual risks" section before deploying. Highlights:

- **Admin 2FA (TOTP) is now implemented** and mandatory: `npm run create-admin`, then `npm run enroll-totp --workspace apps/admin-api -- --email you@example.com` (scan the printed key). Codes are single-use; the secret is encrypted with its own `ADMIN_TOTP_ENCRYPTION_KEY` (never the client-token key). Production refuses to boot with `ADMIN_REQUIRE_TOTP=false`.
- Fixed a **process-crash** bug (a DB error in the auth middleware killed the whole API, bots included), several **financial-flow** bugs (an ambiguous withdrawal failure deleted its own record; audit failures after money moved reported a failed trade), a missing `DELETE` grant that would have broken admin sign-out, and WebSocket abuse/lifecycle gaps.
- Added login throttling + timing-equalisation, per-user trade limiters, a double-buy guard, correlation ids (`X-Request-Id`), JSON error mapping, production-config refusals, and `infra/nginx/security-headers.conf` for the static apps.
- **New environment variables:** `TRUST_PROXY` (api + admin-api; set it, usually `1`, behind a load balancer), `ADMIN_TOTP_ENCRYPTION_KEY` and `ADMIN_REQUIRE_TOTP` (admin-api). Production now refuses to boot on `change_me_*` DB passwords, non-https origins, placeholder secrets, or 2FA off (`scripts/apply-roles.sh` can set real role passwords via `DERIVDESK_API_DB_PASSWORD` / `DERIVDESK_ADMIN_DB_PASSWORD`).
- ~~Operate with exactly one API instance running bots~~ — superseded in Phase 10 by a database lease (see the Phase 10 section and docs/security-review.md).
- Tests: api 224, admin-api 78; all four apps typecheck and build. This is a code review, not a penetration test, and was never run against live infrastructure.
